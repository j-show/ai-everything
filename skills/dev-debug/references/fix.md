## 1. 依赖与执行方式 ⛔ BLOCKING

按 Step 0 的登记入口规则检查下列五项；缺失或不可读时停止修复，保留已确认文档。提示在 ai-everything 仓库运行 `npm run upgrade:skill -- --skill <缺失技能名>`，再部署并确认当前会话可调用；不自动安装。

| 技能 | 加载时机与职责 |
| --- | --- |
| `systematic-debugging` | 调查开始前加载，执行复现、证据收集、模式分析、假设验证及失败回退 |
| `test-driven-development` | 写测试和修复前加载，包括它要求的参考文件，验证红 → 绿 |
| `requesting-code-review` | 每个修复任务和整体完成时加载，连同其审查模板检查行为与实际差异 |
| `receiving-code-review` | 收到反馈后、修改前加载；核实再处理，无反馈不调用 |
| `verification-before-completion` | 修复阶段开始即加载，约束后续每次成功声明，并用于最终验收 |

执行方式未明确时问一次并等待；本轮或此前已有明确选择直接沿用：

```text
按 docs/<dd-id>/requirement.md 的已确认编号修复，选择哪种执行方式？
1. 当前会话修复，独立子代理审查（推荐）
2. 子代理修复，由另一个子代理审查
3. 全部当前会话执行（自审，缺少独立审查）
```

三种方式覆盖同一批编号。旧式「是」对应 2，「否」或拒绝所有子代理对应 3。派发不可用时告知并转为 3。方式 3 显式覆盖 requesting-code-review 的强制派发要求：仍按其模板自审，报告独立审查未执行，不能冒充通过。

## 2. 固定范围与交接

重读 requirement.md、工作区和暂存区，记录任务开始状态，保留用户原有及后续编辑。文件存在或「未决：无」不等于新内容已获批准；变化影响已确认行为时回 Step 3 确认。范围只含已编号行为，非目标和未决项不修。不写 proposal.md，不调用 brainstorming 或 writing-plans；不创建分支或提交，除非用户明确要求。

在会话记录「任务 → B 编号 → 文件边界 → 复现与验证命令」，不新增计划或调查报告文件。调查证据记在会话；必要的事实摘要可追加 requirement.md，标为技术证据，不改写已确认行为。

派发不继承会话历史，提供 dd-id、文档路径、编号及非目标原文、文件边界、已有证据、依赖登记入口、本文件和验证命令。实现者不能兼任独立审查者。协调者核对实际差异与验证结果，不直接转述代理成功声明。

## 3. 根因调查 → 最小修复

执行 systematic-debugging 的四阶段，技术调查不由需求访谈代替：

```text
复现原始现象 → 追踪数据与边界 → 对比正常路径
    → 单一假设 + 最小实验 → 根因证据
    → TDD 有效失败测试 → 最小修复 → 通过及相关回归
```

每次只检验一个假设，写明证据如何支持或推翻它。改变产品代码的实验优先在隔离副本执行；原位实验开始前保存受影响内容及本轮差异，作为恢复依据。

无论实验成功或失败，都先撤回本轮实验改动，再从缺陷仍在的基线执行 TDD；已在同一状态取得有效红灯、且实验就是对应最小修复时，保留改动并验证绿灯，无须为流程重做。临时插桩完成用途后移除。

🔴 STOP：恢复前重读文件并对照实验前态及本轮差异。用户后续编辑与实验改动可分离时只撤回实验；内容重叠或缺少可确认前态时保留现场，报告冲突并暂停受影响修复，请用户确认保留内容。不得整文件覆盖、重置工作区或把无法恢复说成恢复成功。

| 触发条件 | 动作与出口 |
| --- | --- |
| 无法复现或证据不足 | 补环境、日志、输入及触发步骤；暂停修复，不猜原因或添加掩盖症状的兜底 |
| 调查假设被推翻 | 恢复本轮实验后形成新假设；调查实验失败不计入实际修复失败次数 |
| 实际修复无效 | 回到调查，累计同一缺陷的修复失败次数；三次失败后停止继续修补，先与用户讨论架构，换代理或续跑不清零 |
| 确认是环境、时序或外部因素 | 记录已排查证据；处理方案仍须符合编号，新增重试、超时等行为先回 Step 3 确认 |
| 根因要求改变已确认行为或扩大范围 | 暂停受影响修复，回 Step 3；确认后重新建立测试与修复范围 |
| 测试无法有效运行 | 优先已有设施、语言内置工具或最小复现脚本；仍阻塞则停止受影响修复，报告条件，不自动装框架 |

按 test-driven-development 先运行可观察行为测试，确认因原始缺陷失败，再做最小修复。导入错误、缺依赖、零测试不是有效红灯；已有测试能复现时直接复用。用户原有或已验收的正确实现不能为制造红灯而删除；若接手已修代码，红绿对照放隔离副本，不撤回用户代码。本轮临时实验按上述恢复规则处理。通过后只做必要整理并回归，不夹带重构。

完成：每个修复有「编号 → 原始复现 → 根因证据 → 红绿结果」，否则保持阻塞或待调查状态。

## 4. 审查与反馈闭环

加载 requesting-code-review 及其模板。提供编号、非目标、根因证据、准确差异、测试结果和缺口。审查覆盖本轮暂存、未暂存、新增文件及必要调用方；用任务开始状态区分用户既有改动。只有真实提交范围完整覆盖本轮内容才用 BASE/HEAD，不能照搬 `HEAD~1..HEAD` 或为审查创建提交。审查只读。

有反馈时先加载 receiving-code-review，对照代码、测试和编号核实：

| 结论 | 处理 |
| --- | --- |
| 成立且范围内 | 行为缺陷回到根因调查及 TDD；非行为性修改用对应检查验证；处理后复审 |
| 建议错误或违背已确认行为 | 提供证据并请审查者复核，不盲改、不重复询问已明确决定 |
| 含糊或无法验证 | 澄清并暂停受影响项；无法确认相互独立时暂停整组反馈 |
| 新行为或越界建议 | 记录为本轮不采纳；用户明确要求采纳才回 Step 3 确认编号 |

上述分组显式限定 receiving-code-review 的全组停止规则：明确越界的建议不阻塞独立且证据充分的范围内修复；不能用分组掩盖相关疑点。逐项处理并验证，带证据复审；成立的 Critical / Important 未解决不得进入下一任务或宣称完成，Minor 记录处理或保留理由。重复争议无新证据时报告阻塞，不盲目重试。审查模板中的合理预期可用于发现问题，不授权扩展编号。

完成：审查反馈有逐项处置及复审结论；自审方式如实标注，不能自称获得独立审查通过。

## 5. 整体审查与最终验收

所有任务完成后审查整体差异及集成，有反馈继续闭环。单任务且最终状态与任务审查完全一致时，可复用该审查。

按 verification-before-completion 核对最终状态：

- 原始缺陷复测及相关回归有证据；每个 B 编号对应实现位置和验收结果，测试绿不自动代表全部行为满足。
- 执行与修改相称的测试、构建、静态检查，读取完整输出、退出码及测试数量。本编排显式允许复用本轮覆盖充分且仍对应最终状态的证据；后续修改使证据失效时重跑受影响检查，不用过期结果宣称通过。
- 核对最终差异、用户改动保留及目标仓库要求的文档同步。
- 交付列出修复编号、根因摘要、实际验证命令和结果、未执行检查、环境阻塞、审查方式及剩余问题。未验证或阻塞不得表述为全部完成。
