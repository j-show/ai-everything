# 修复

只在 Step 4 读取：requirement.md 的「未决」为「无」，且用户没有要求停在文档。

改产品代码之前，问一次并等待。不再另问「要不要开始改代码」：

```text
是否创建子代理，按 docs/<dd-id>/requirement.md 里已编号的已确认行为修复？
回答「否」就在当前会话直接修复，范围不变。
```

两种回答覆盖同一批编号。未决项不修。不新增编号之外的行为。不创建提交，除非用户在本需求里明确要求提交。不写 proposal.md，不调用 brainstorming 或 writing-plans。

拿不准两种回答的范围时，读 `references/examples.md` 的「子代理」。

## 创建子代理

派发一个修复子代理，覆盖全部已编号行为。提示词里写上：

- `dd-id`
- `docs/<dd-id>/requirement.md` 的路径
- 「已确认行为」的编号原文
- 「非目标」原文

子代理不继承本会话的对话历史。它先指出与每条编号不符的现有代码，或指出缺了哪一段，再只做让这些编号成立的改动。非目标里的改动不做。结束时列出：修复了哪些编号、跑过的验证命令和结果、没跑的验证。

## 当前会话直接修复

用户回答否时，在当前会话修复，范围与创建子代理相同。

修复前重读 requirement.md，保留用户在澄清后的修改。问自己：哪一段现有代码让这条编号不成立？若是缺了逻辑，缺的是哪一段？先指出，再改或补上。非目标里的改动不做。每条已编号行为都能在 diff 里指出对应改动。仓库里已有能覆盖这些行为的测试命令就跑它。没有这样的命令时，完成说明写明未验证，不为此新装测试框架。

## 派发不可用

用户回答是，但当前会话没有子代理派发能力：说明派发不可用，然后在当前会话按同一范围修复。
