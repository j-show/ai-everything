# 编写缺省

只在 Step 3 读取。与目标文件相邻代码冲突的条目不要套用。

## 不可变

创建新值。不要就地修改调用方之后还会使用的对象。

```text
WRONG:  modify(original, field, value)  → 改动 original 本身
CORRECT: update(original, field, value)  → 返回带有该改动的新副本
```

局部变量在返回前的组装可以更新；不要把这个更新泄漏到入参、缓存或模块级对象。

## KISS、DRY、YAGNI

- 采用能正确完成请求的最直白写法。先保证读得懂，再考虑更快。
- 同一逻辑在本次改动里已经出现第二次、并已开始发生分歧时，抽成函数。
- 只被一种情况使用的参数、接口层次或扩展点，不要提前加上。

## 文件与函数

- 按功能或领域放文件，让同一变化原因的代码待在一起。
- 源文件通常 200–400 行。800 行是可维护性软上限。测试、生成文件和第三方代码可以更长，但要能指出原因。
- 函数保持单一职责，以大约 50 行为上限。超过时按职责拆开。
- 条件开始叠到第 4 层时，改为提前返回。
- 有含义的阈值、延迟和上限使用具名常量。

## 错误

- 每一层都处理自己能处理的失败，其余用现有错误类型继续传递。
- 面向用户的文案说明下一步；服务端日志保留操作、输入标识和失败原因。
- 不要用空返回值表示失败。

## 边界校验

在系统边界校验，再把数据交给内部逻辑：

- 用户输入、接口响应和文件内容都算外部数据。
- 仓库已有模式校验时使用它。
- 非法输入立即失败，错误信息指出哪个字段不合法。

## 命名

- 名字要能单独说出它保存什么或做什么。
- 布尔名读起来是一个判断。
- 常量、类型和普通值的外形差异，跟随当前语言在本文件里的现成写法。

## 新边界的缺省形状

仓库已经有数据访问或响应形状时，沿用已有形状，忽略本节。

数据访问边界使用稳定操作，让业务代码依赖这组操作，而不是依赖存储细节：`findAll`、`findById`、`create`、`update`、`delete`。具体存储可以是数据库、接口或文件。

新的 HTTP 响应使用同一信封：成功或状态标记、数据（失败时为空）、错误信息（成功时为空）。分页额外带 `total`、`page`、`limit`。
