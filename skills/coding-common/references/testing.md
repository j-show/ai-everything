# 测试

只在 Step 4 读取。使用仓库已有的测试框架和命令。仓库没有测试框架时，不新装框架；行为变更在完成说明里标明未测试及原因。

## 何时写新测试

- 可观察行为变化：先写测试。包括新功能、缺陷修复和对外错误变化。
- 纯重构：只跑已有测试。
- 注释、格式、用户指定文案：不新增测试。

## 行为变更的顺序

1. 写一个描述期望行为的测试。它应当在实现完成前失败。
2. 运行它，确认失败原因是行为尚未实现，而不是拼写错误或装不上的依赖。
3. 写刚好让它通过的实现。
4. 再运行它，确认通过。
5. 在测试仍通过的前提下整理命名和结构。
6. 运行本次改动相关的已有测试。

缺陷修复的第一个测试应当复现用户描述的失败。

## 覆盖率

项目已有覆盖率命令时，本次改动触及的代码以 80% 为最低线；项目门槛更高则跟随项目。

没有覆盖率命令时，报告“未测量”。不要为了这一条安装新工具。不要把“测试跑过”写成“覆盖率达标”。

## 失败时查什么

测试失败时按这个顺序看：

1. 测试是否依赖了执行顺序、真实时钟、网络或未隔离的全局状态？
2. 替身是否把被测行为一起替掉了？
3. 实现是否与已确认的期望不符？

期望仍然符合请求时，改实现。期望写错或请求已经变了时，才改测试，并在说明里写原因。

## 结构与命名

用准备、执行、断言三段。名字写出条件和结果，例如：

- 没有匹配项时返回空列表
- 缺少必要配置时失败
- 主路径不可用时走已有的后备路径

断言检查行为。不要断言无关的内部调用次数。
