# Coding Common

IRON LAW: 实现以目标文件及其相邻代码为准。本技能的 references 只填补仓库里不存在的缺省。禁止到本技能目录之外去找一份通用规范来覆盖仓库写法。

红线（出现就停，先改再继续）：

- 为了“更规范”改写请求范围外的文件
- 用新依赖替换仓库里已有的实现，或替换大约十行以内能写清的本地逻辑
- 就地修改入参或共享对象
- 吞掉错误、留下调试输出、把密钥写进源码
- 行为已经变化，却补一个当前实现下永远通过的测试
- 没有覆盖率命令输出，却声称达到 80%

## Workflow

复制这份清单并逐项勾选：

```
Coding Common Progress:

- [ ] Step 0: 对齐仓库写法 ⛔ BLOCKING
- [ ] Step 1: 判定改动类型 ⚠️ REQUIRED
- [ ] Step 2: 越界确认（仅在触发时）
- [ ] Step 3: 按 style 实现 ⚠️ REQUIRED
- [ ] Step 4: 验证行为 ⚠️ REQUIRED
- [ ] Step 5: 安全敏感改动按 security 自检（条件）
- [ ] Step 6: 完成前按 review 自检 ⚠️ REQUIRED
- [ ] Step 7: 提交说明（仅当用户本轮要求提交或开 PR）
```

**控制流**

1. Step 0 未完成，不改文件。
2. 用户写明的行为与相邻写法一致时，直接实现。Step 2 任一问为「是」则停。
3. 行为会变化时，Step 4 先有失败测试，再写通过它的最小实现。
4. Step 6 未完成，不把任务标成完成。

## Step 0: 对齐仓库写法 ⛔ BLOCKING

读即将修改的文件，以及同目录或同模块里最近的同类文件。记下这些事实；后面的缺省不得覆盖它们：

- 命名、导出方式和目录是按功能还是按类型组织？
- 错误是抛出、返回结果对象，还是交给现成的错误类型？
- 数据访问、接口响应、日志分别用的是哪一种现成写法？
- 测试放在哪里，用什么命令跑相关测试？
- 仓库里是否已经有可复用的函数？有则扩展它。

仓库还没有该类文件时，缺省以 `references/style.md` 为准。

## Step 1: 判定改动类型 ⚠️ REQUIRED

| 类型 | 判定问题 | 接着读取 |
| --- | --- | --- |
| 行为变更 | 调用方能观察到的结果、错误或副作用会变吗？ | `references/style.md`、`references/testing.md` |
| 纯重构 | 结果保持不变，只是在拆函数、改名字或挪代码吗？ | `references/style.md`；跑已有测试，不新增投机测试 |
| 安全敏感 | 改动是否碰鉴权、用户输入、查询、文件路径、加密、支付或出站请求？ | 再读 `references/security.md` |
| 无行为 | 只改注释、格式或用户指定的文案吗？ | `references/style.md`；不新增测试 |

一次改动可以同时属于多行。只读命中的 reference。

## Step 2: 越界确认 🔴 CHECKPOINT · 🛑 STOP

先回答下面三问。任一为「是」就停住。同一句里点了名，也不能跳过这一步。

1. 不新增依赖就无法完成，而仓库没有可复用实现？
2. 对外行为会变，但用户没有写明新行为？
3. 缺陷修复之外，还要求顺手改风格、统一响应或重写相邻文件，并且这和当前文件的写法冲突？

停住时只写两句：已经完成的部分；尚未改动的扩大项。下一条消息里没有明确的「确认扩大」之前，不改那些文件。

| 触发 | 一线修复 | 仍失败则 |
| --- | --- | --- |
| 同一句里既有缺陷修复，又有与相邻写法冲突的顺手重写 | 只修缺陷，并先写会失败的测试 | 下一条未确认扩大 → 风格和响应格式保持原样 |
| 必须新增仓库里没有的依赖 | 用现有代码完成能完成的部分后停住 | 下一条未确认依赖 → 不安装 |

其余情况直接进入 Step 3。不要为了开始实现而再问一次。

## Step 3: 按 style 实现 ⚠️ REQUIRED

实现前读完 `references/style.md`。问自己：

- 这个函数是在返回新值，还是在改调用方还要继续用的对象？
- 失败发生时，调用方能看到明确错误吗？服务端日志里有定位上下文吗？
- 外部数据（用户输入、接口响应、文件内容）在进入逻辑前校验了吗？
- 有没有只出现一次、却被提前抽成框架的抽象？

新的数据访问边界或 HTTP 接口，仅在仓库没有现成形状时使用 style 里的缺省形状。

## Step 4: 验证行为 ⚠️ REQUIRED

行为变更：读 `references/testing.md`，按其中的顺序写测试并运行仓库已有的相关测试命令。

纯重构或无行为改动：运行能覆盖被改代码的已有测试。没有这样的测试时，报告“未运行”，不要为了凑覆盖率新装工具或新写永远通过的测试。

没有测试命令、命令失败或环境缺依赖时，完成说明里写明实际命令、退出状态和未验证的行为。

## Step 5: 安全敏感改动

读 `references/security.md` 并逐项核对本次 diff。发现密钥、拼接进查询的外部输入、或把敏感细节返回给调用方时：停止继续加功能，先从本次改动里去掉该问题，再在被改文件中查找同一种写法。不要在回复或日志里打印密钥值。需要轮换时告诉用户轮换哪一类密钥。

## Step 6: 完成前自检 ⚠️ REQUIRED

读 `references/review.md`。CRITICAL 或 HIGH 仍留在本次 diff 里时，任务未完成。MEDIUM 在不扩大范围的前提下修。LOW 只在用户要求整理风格时修。

## Step 7: 提交说明

用户本轮没有要求提交或开 PR 时，跳过这一步，不要执行 git commit 或 git push。

提交说明使用：

```text
<type>: <description>

<optional body>
```

`type` 取 `feat`、`fix`、`refactor`、`docs`、`test`、`chore`、`perf`、`ci` 之一。描述写行为变化。

用户要求开 PR 时：阅读该分支相对基线的全部提交，用三点差异看完整改动，摘要包含测试计划。用户没有要求推送时，不推送。

## 诚实边界

- 不规定某种语言的大小写、前缀或框架惯用法；这些以当前文件为准。
- 不选择测试框架，不安装仓库没有的覆盖率工具。
- 不编排代理，不配置会话钩子，也不选择模型。
- 自检范围是本次 diff，加上被改文件里的同类写法。它不是全仓库审计。
- 仓库写法与本技能缺省冲突时，跟随仓库，并在完成说明里写明冲突的那一条。

## Anti-Patterns

- 先写实现，再补一个断言当前返回值的测试
- 捕获异常后返回空值、空列表或默认成功
- 为了 DRY 把两段只是长得像的逻辑合成一个带布尔开关的函数
- 在现有模块已经用列表追加、记录更新或构建器时，把无关代码改成另一套不可变风格
- 把接口统一包进新的响应信封，尽管仓库已有自己的响应形状
- 留下只在调试时才有意义的打印
- 用本技能目录之外的规则文件解释为什么这样写

## Pre-Delivery Checklist

- [ ] 命名、错误、数据访问和测试位置与相邻代码一致；不一致处已在说明里点明
- [ ] 新逻辑返回新值，不改入参和共享对象
- [ ] 外部输入在使用前失败，失败信息能让调用方判断原因
- [ ] 行为变更有先失败、后通过的测试；相关命令的退出状态写在说明里
- [ ] 未声称未经命令输出支持的覆盖率
- [ ] 安全敏感 diff 已按 `references/security.md` 核对，且不含密钥字面量
- [ ] diff 中没有未处理的 CRITICAL 或 HIGH
- [ ] 未新增用户未要求的依赖，未提交用户未要求的 commit
