# skill-review：审查技能质量

检查一个技能的目录、描述、工作流、上下文成本和常见反模式，给出具体且可执行的改进建议。重点是提示词能否正确选中技能、代理能否按流程完成工作，以及关键约束是否清楚。

## 触发提示词

`review skill`、`audit skill`、`skill quality`、`check my skill`、`evaluate skill`、`skill lint`、`validate skill`、`skill review`、`is this skill good`、`improve this skill`。

> 使用 skill-review，审查 skills/my-helper，指出触发描述和工作流的问题。

> 检查这个 skill 的质量，只给可执行建议。

它审查技能说明；普通业务代码审查应使用相应代码审查技能。

## 内部流程

```mermaid
flowchart LR
    A[通过路径、当前目录或名称定位] --> B[读取 SKILL.md 并列出资源]
    B --> C[按五个维度分析]
    C --> D[列出具体 Strengths]
    D --> E[按影响排序 Suggestions]
```

1. 接受显式路径、当前技能目录，或按名称在工作区搜索。读取完整 SKILL.md，列出目录文件并统计入口行数。
2. 加载 review-criteria，检查五个维度：

| 维度 | 主要检查 |
| --- | --- |
| 结构 | 入口、name 与目录一致、描述、元数据、脚本用途、引用深度及无实际作用文件 |
| 描述 | 路由能否仅凭 description 明白适用任务，是否包含自然请求与触发词 |
| 工作流 | 可跟踪清单、顺序、阻塞前提、条件分支、确认与可观察终点 |
| 上下文成本 | 关键约束是否前置、reference 是否按需读取、是否重复说明常识和依赖正文 |
| 反模式 | 模糊要求、残留占位、过度规定、缺失边界或交付检查、入口过长 |

3. 输出先给 Strengths，至少两条且引用具体有效设计；再给按影响排序的 Suggestions。每条建议包含 What、Where、Fix，必要时给前后对比。

## 路由与规则的适用范围

- 显式路径优先；只有名称时先定位目标，不能直接审查整个仓库。
- 本技能本身只定义分析与建议输出，没有自动修改、反复复审或打包步骤；这些由 skiller 等外层流程负责。
- 审查参考包含入口 500 行限制、接近 400 行提醒、描述长度与触发词数量等启发式，也检查文件、引用和确认节点。它们是审查依据，不能替代真实需求判断。
- 当前入口提醒警惕关键词堆砌，而详细参考也鼓励多种触发表达。报告应指出具体路由收益或冗余，避免只按词数判质量。
- README 等文件需要有实际用途。本仓库按用户要求提供面向人的说明，不能仅因存在 README 就判为无用或建议删除。
- 不把技能有意省略的能力当缺陷，不提出纯个人风格意见，不以“可以更好”代替具体改法。

## 输出与文件导航

默认交付 Strengths 和 Suggestions；少量建议平铺，超过五条时可按维度分组。没有规定必须落盘报告，也不应把文档审查当作已运行行为测试。

- [SKILL.md](SKILL.md)：定位、五维分析与报告格式。
- [review-criteria.md](references/review-criteria.md)：结构、描述、流程、上下文和反模式的详细标准。
