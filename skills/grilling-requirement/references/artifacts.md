# 标识、续跑与需求产物

固定 ID、恢复任务或写 requirement.md 时读取。

## task-id

新任务使用 `<pre-tag>-<YYYYMMDD>-<feature-name>`。

- pre-tag 默认 `TK`，可由用户或调用方指定；调用方 dev-requirement 使用 `DR`，dev-debug 使用 `DD`。前缀接受字母数字（首字符为字母），保留指定大小写；空值、路径分隔符或其他字符需澄清，不直接用于路径。
- 日期取用户时区本轮开始的日历日期：四位年、两位月、两位日，例如 2026-10-28 → `20261028`；跨午夜不改。
- feature-name 使用小写英文与数字，单个连字符分隔，首尾无连字符；只对 feature-name 归一化驼峰、下划线与空格。名称来自功能或缺陷现象，不预设规则或根因。不能唯一确定时只问一次并等待。
- 用户提供符合格式且与调用方前缀一致的完整 ID 时照用，不改日期；前缀冲突或非法日期须先澄清。宣布 ID 后固定，不在同次任务中重算。
- 目标项目是用户正在工作的项目根目录，不是技能安装目录；目标不明确时先确认。

## 继续已有 task-id

明确指定续跑时沿用 ID 和已确认选择；既有六位日期的历史 ID 仅用于原目录续跑，不自动迁移或重命名，新任务一律八位日期。目录已存在但意图不明时，只问继续还是换 feature-name，禁止直接覆盖。

读取现有需求、用户确认记录和当前指令，核对内容与已确认版本，并识别本轮输入中尚未落盘的新增/变更要求。文件存在不等于已经批准；读取失败不能视为空文件，先取得可读内容或该文件全文替换授权。保留暂存、已有与后续用户编辑。

| 证据 | 下一步 |
| --- | --- |
| 没有需求稿 | Step 2 |
| 需求稿在，缺书面完成记录、内容有未确认变化，或本轮有尚未落实的新增/变更要求 | Step 3，仅处理受影响条目 |
| 书面澄清有明确完成记录，当前内容一致、未决为无，且本轮无尚未落实的要求 | 返回调用方或交付，不重复访谈 |

必要文件缺失或确认记录与当前内容不符时说明缺口，回对应步骤。只补问影响下一步的缺失信息。方案批准、实现或修复进度由调用方处理，不以需求完成推断后续批准。

## requirement.md

路径：`docs/<task-id>/requirement.md`。

```markdown
# <task-id>

## 用户原话

<用户描述功能或缺陷的原句，不改写意图>

## 已确认行为

- B1. <在明确条件下可观察的一条行为；缺陷任务写修复后的预期结果>
- B2. <一条可观察的行为>

## 非目标

- <用户明确排除的行为；没有则写「无」>

## 未决

无。
```

编号从 B1 连续递增。一条行为只写一件可验收的事。尖括号是填写位，写入文件时换成实际句子，不留下尖括号。

Step 2 在 grilling 前沿已空、用户确认共同理解之后创建该文件。当时「未决」就写「无」。

Step 3 按主流程待处理清单限定范围。改已有编号措辞或增删行为，都要有用户确认依据；不受影响的编号保持不变，新增行为接续现有最大编号，避免为补新行为重排旧编号。用户没确认的改写不落盘。解决掉的问题写入「已确认行为」或「非目标」，不留在「未决」。

问自己：一个没参加访谈的实现者，能否只靠编号判断做完没有？不能则这条还要拆开或改写，并再请用户确认。


写入前重读目标；已有文件仅按已确认范围更新，保留无关内容。不可读时暂停写入，不覆盖。新增行为经用户确认后编号，不在方案或代码中偷偷扩展。
