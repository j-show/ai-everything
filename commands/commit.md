# 根据改动总结提交信息，并创建 commit

## 安全约束（必须遵守）

- **不要**修改 `git config`。
- **不要**使用破坏性 git 操作（如 `git push`、`git rebase`、`git reset`、`git cherry-pick` 等）。
- **不要**跳过钩子（`--no-verify`、`--no-gpg-sign` 等），除非用户明确要求。
- **不要**随意使用 `git commit --amend`；仅在用户规则明确允许时再用（核对作者、未推送、钩子失败后的处理等）。
- **不要**暂存或提交明显含敏感信息的文件（如 `.env`、凭据、私钥）；应提醒用户并排除。

## 步骤

### 1. 收集信息（并行执行）

- `git status`（未跟踪文件与分支状态）
- `git diff`（已暂存与未暂存）
- `git log -n 15 --oneline`（参考近期用词与习惯；**提交结构**一律按下文固定格式）

### 2. 给用户写简洁说明

- 用一小段或若干条要点说明「改了什么、为什么改」（意图），避免堆砌文件列表。
- 说明内容应能自然映射到下节「提交说明」中的**标题**与**列表项**。

### 3. 拟定提交说明（固定格式）

**整体结构**（空行不可省略）：

```text
{类型}: {标题}

- {内容1}
- {内容2}
```

- **第一行**：`{类型}: {标题}`，类型与标题之间有一个空格；标题要求**精简、概要**。
- **正文**：从第二段开始，每行一条以 `- ` 开头的列表；每条是对所做改动的**简单概要**（几条即可，不必穷举文件，但需要涵盖本次改动的主要意图）。
- 若只有一项改动，可只保留一条 `- `；若无须展开，至少保留一条概括性列表项。

**类型**（必选其一，含义如下）：

| 类型       | 用途                         | 判定要求                                           |
| ---------- | ---------------------------- | -------------------------------------------------- |
| `fix`      | 修复 bug                     | 小范围业务代码改动。                               |
| `feat`     | 新增/修改功能                | 新增/修改业务代码，并形成完整功能。                |
| `docs`     | 纯文档、`README`、JSDoc 改动 | 仅`README`、JSDoc 改动，不涉及业务代码。           |
| `ci`       | 纯 CI 脚本调整               | 仅 CI 脚本改动，不涉及业务代码。                   |
| `refactor` | 重构代码                     | 大范围业务代码改动，调整代码结构，不形成完整功能。 |
| `style`    | 样式调整                     | 样式调整，不涉及业务代码。                         |
| `perf`     | 性能优化                     | 性能优化，调整代码结构，不形成完整功能。           |
| `test`     | 测试用例变更                 | 测试用例变更，不涉及业务代码。                     |
| `build`    | 构建系统或工具变更           | 构建系统或工具变更，不涉及业务代码。               |
| `revert`   | 回滚提交                     | 回滚了某个提交或功能。                             |
| `chore`    | 其他杂项                     | 其他杂项，编码变更、包版本变更、依赖更新等。       |

权重顺序：`refactor` > `feat` > `fix` > `chore`。
选择类型时，优先考虑本次改动的主要意图，存在多个时按改动意图的占比选择，除非用户在 `{{input}}` 中指定了类型。

**落库**：本格式含换行与列表，须用 `<<'EOF'` … `EOF` 多行提交（勿用单行 `-m` 硬塞）：

```bash
git commit -m "$(cat <<'EOF'
feat: 示例标题

- 示例：做了什么事
- 示例：还影响了什么
EOF
)"
```

在 `-m "..."` 中注意转义；提交说明内避免出现未转义的 `"`。

### 4. 暂存与提交（顺序执行）

1. `git add` 只加入本次改动相关文件（避免无关噪音）。若状态里均为本次工作，在「范围最小且仍能完整提交意图改动」的前提下选择 `git add -A` 或显式路径。
2. 使用上文 `<<'EOF'` 多行形式执行提交（本格式含换行，不适用单行 `-m`）。
3. 再执行 `git status`，确认工作区符合预期（干净或仅剩有意保留的未提交项）。

### 5. 若钩子失败

- 按用户策略：**不要**对失败或被钩子拒绝的提交使用 `--amend` 改写。
- 修复问题（如静态检查、格式化、测试），必要时重新暂存，并**新建**一次提交。

## 向用户输出

- 展示改动说明摘要。
- 展示实际使用的提交命令或最终提交说明全文。
- 成功后简要展示 `git status` 结果（例如：工作区干净、或领先远程 N 个提交）。
