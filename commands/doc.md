# 根据实现补全 JSDoc、关键步骤注释与 README

## 用户目标

根据实现代码，对每个函数、常量、类型、枚举、接口补充 jsdoc，并对代码片段的关键步骤增加注释，同时完善 README 文档

## 原则（必须遵守）

- **实现优先**：先读代码与调用关系，再写文档；JSDoc 描述的是**当前行为**，不是理想设计。
- **少而准**：注释解释「为何 / 边界 / 不变量」，避免复述标识符或显而易见的语句。
- **README 与源码分工**：README 写入口、安装运行、配置、架构、导出功能与使用示例；不要把每个函数说明书搬进 README。
- **忽略目录**：不处理 `test`、`tests`、`e2e`、`dist`、`coverage`、`.cursor` 目录下的文件。
- **README 输出**：如果存在 README_CN.md 文件，则 README.md 为英文版，README_CN.md 为中文版（并相互关联），否则只输出 README.md（仅输出中文版，除非用户明确要求输出英文版）。

## 执行顺序

1. **摸底**：入口文件、导出的公共 API、`package.json` 脚本、已有 README 段落。
2. **补充JSDoc**：按文件逐个函数、类、接口、类型、枚举、常量补齐（含未导出但复杂或复用多的内部函数，若用户未限定「仅 public」则默认全量）。
3. **函数内注释**：仅在关键步骤（递归逻辑、算法分支、资源生命周期、并发/顺序假设、魔法数含义、与外部系统契约）添加简短行内或块注释，写「为什么」而非「做什么」。
4. **README**：与代码同步（命令、环境变量、目录结构、扩展方式）；新增「开发说明」时可链接到源码而非大段粘贴。

## 函数内注释 约定

- 不为了注释而注释，注释的目的是为了帮助理解代码逻辑，而不是为了满足注释的数量。
- 不为了写注释，改变代码结构，不要把注释写成代码。
- 在关键步骤（递归逻辑、算法分支、资源生命周期、并发/顺序假设、魔法数含义、与外部系统契约）添加简短行内或块注释，写「为什么」而非「做什么」。
- 注释内容必须与代码逻辑一致，不能出现「我以为」、「我觉得」、「可能」等主观猜测。
- 非定义式的匿名函数，必须补充注释，注释写在函数内容最前面。

## JSDoc 约定

- 每个函数、类、接口、类型、枚举、常量都应补充 JSDoc，interface 的属性也需要补充 JSDoc。
- 每个函数至少：**一句话描述**；有参数则 `@param`；有返回值则 `@returns`；可能抛错则 `@throws`；异步则写明 Promise 解析类型。
- **TypeScript**：优先依赖类型签名；JSDoc 补充类型表达不清的语义、副作用、单位（ms/px）、默认值。复杂对象用 `@typedef` 或指向已有类型。
- **示例**：仅对非直观用法、公共 API、导出函数、类公共函数 提供 `@example`；避免冗长。
- **overload 的函数**：必须给出所有参数的示例。
- **第三方库**：当文档涉及某库的公开 API、标签或迁移行为时，先用 Context7（`resolve-library-id` → `query-docs`）核对再写，避免过时用法。

## 何时不写注释

- 单行自解释赋值或标准模式（如 `const x = items.map(...)` 且命名清晰）。
- 用 JSDoc 已说清楚的契约，不在函数内重复同一句话。

## README 检查清单

- [ ] 项目名称与一句话定位
- [ ] 环境要求（Node 版本等）
- [ ] 安装与常用命令（与 `package.json` 一致）
- [ ] 配置与环境变量（表格或列表）
- [ ] 目录结构和职责概览
- [ ] 导出功能、导出函数、类公共函数的使用示例

## 完成前自检

- [ ] JSDoc 与实现一致（分支、可选参数、空值）
- [ ] 未引入「计划支持但未实现」的虚假 API 描述
- [ ] README 中的路径与脚本名可在仓库中验证
